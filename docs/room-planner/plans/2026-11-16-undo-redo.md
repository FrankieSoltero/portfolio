# Undo and redo (slice E) Implementation Plan

> **For executors:** execute with soltero-skills:lean-sdd. The Task Dependency
> Table below is the scheduling and review-depth contract.

**Goal:** Every edit to the plan can be taken back and put back, one visitor-sized step at
a time, with the keyboard and with two header buttons.

**Spec:** `docs/room-planner/specs/2026-11-16-undo-redo-design.md` (approved by the owner
on 2026-11-16).

**Architecture:** One new module, `room-planner/state/historyStore.ts`, subscribes to the
plan store and keeps two lists of earlier plans. It decides whether a change opens a new
step or joins the current one from two signals the UI gives it: an open *group* (a drag, or
a visit to a text field) and a *key* (a run of key presses on one thing). Undo and redo put
an earlier plan back through the plan store's existing `reset`. Nothing new is stored in
the plan; the saved format stays at version 3.

**Tech stack / test runner:** Next.js 15, React 19, TypeScript, Zustand 5, Vitest + React
Testing Library + jsdom. One file: `npx vitest run <file>` from the repo root. Everything:
`npm run check` (typecheck, lint, tests, build). Repo root:
`/Users/franciscosoltero/Desktop/Code/Portfolio Website`. Branch: `undo-redo`.

## Global Constraints

- The plan store never changes a document in place; a step is a set of references to an
  earlier `room`, `items`, `openings` and `obstacles`. The history never copies or edits them.
- `units` and `schemaVersion` are never part of a step. Undo and redo keep the current ones.
- The history is in memory only. Nothing is written to storage and nothing is sent anywhere.
  No change to `planSchema.ts`, to `browserPlanStore.ts` or to the key `room-planner:plan:v1`.
- New CONFIG values, exact: `historyLimit: 100`, `historyMergeMs: 1000`.
- Announcement texts, exact: `Undone`, `Redone`. Button texts, exact: `Undo`, `Redo`.
- Time is read with `Date.now()` so tests can use Vitest fake timers.
- Nothing under `room-planner/domain/` or `room-planner/view/` imports the history module,
  three.js or React.
- Existing tests pass unchanged unless a task's "Test changes" line names them. Before
  finishing, each implementer greps the tests for every constant, string and element role
  the task adds or changes (lesson 1 of slice D) and reports any pinned test outside its list.
- A test that reads the history calls `clearHistory()` in `beforeEach`.
- Tests first: in Tasks 1 to 5 the tests for the behavior table are written and seen to fail
  before the implementation, and the task report quotes the failing run.
- Rollback: the work is on branch `undo-redo`, one commit per task, and reaches the live
  site only through a pull request the owner merges. Reverting that merge removes the whole
  feature. No feature flag is used, because the history is in memory only and touches no
  stored data.
- Implementers stage only their own listed paths. Commits end with the trailer lines the
  dispatch gives. Never touch `Multiplayer_AI_Sprite.aseprite`.
- No new dependency. `/room-planner` First Load JS stays between 104 and 107 kB; the build
  output of `npm run check` prints it, and Tasks 7 and 9 quote that line.
- A dev server may be running on port 3478. Stop it by port before `npm run check`.

**Test changes:** `catalog.test.ts`, the test `CONFIG has exactly the listed values`, gains

**Interfaces:**
- Consumes: the existing `usePlanStore` (`subscribe`, `getState().reset(doc)`), `useUiStore`
  (`selectedId`, `selectedCornerId`, `selectedWallId`, `selectedOpeningId`,
  `selectedObstacleId`, `select`, `selectCorner`, `selectWall`, `selectOpening`,
  `selectObstacle`) and `CONFIG`.
- Produces: the exports of `room-planner/state/historyStore.ts` below, and
  `CONFIG.historyLimit`, `CONFIG.historyMergeMs`.

```ts
export type GroupKind = 'drag' | 'field';
export interface HistoryState {
  canUndo: boolean;
  canRedo: boolean;
  /** 'Undone' or 'Redone' after the latest undo or redo; null before the first and after clearHistory. */
  lastAnnouncement: 'Undone' | 'Redone' | null;
  /** Goes up by one on every successful undo or redo. */
  announceCount: number;
}
export const useHistoryStore: UseBoundStore<StoreApi<HistoryState>>;
export function undo(): boolean;          // true when a step was taken back
export function redo(): boolean;          // true when a step was put back
export function clearHistory(): void;     // empties both lists, forgets groups, the key and the last step
export function openGroup(kind: GroupKind): void;
export function closeGroup(kind: GroupKind): void;
export function renewFieldGroup(): void;  // an open field group becomes a new group; no effect when none is open
export function runKeyed<T>(key: string, fn: () => T): T;  // runs fn with `key` as the current key, restores the previous key after (also when fn throws)
```

The module subscribes to `usePlanStore` once, when it is first imported.

A "change" is a plan-store update in which `room`, `items`, `openings` or `obstacles` is a
different reference. The "active group" is the open drag group if there is one, otherwise
the open field group, otherwise none.

**Behavior:**

| Case | Input / state | Expected |
|---|---|---|
| First change | empty history, one change | 1 undo step holding the plan before the change; `canUndo` true, `canRedo` false |
| Units only | `setUnits('m')` | no step |
| Same references | a store update that changes none of the four fields | no step |
| No group, no key | two changes | 2 steps |
| Drag group | `openGroup('drag')`, 5 changes, `closeGroup('drag')` | 1 step; `undo()` restores the plan from before the first of the 5 |
| Two drags | open, change, close, open, change, close | 2 steps |
| Empty drag | open, close, no change | no step |
| Field group | `openGroup('field')`, 3 changes | 1 step |
| Field renewed | field open, change, `renewFieldGroup()`, change | 2 steps |
| Renew with none open | `renewFieldGroup()`, change, change | 2 steps (no group was created) |
| Drag inside a field | field open, change, drag open, change, drag close, change | 3 steps: field, drag, and the last change is a new step because the latest step is not the field's |
| Keyed run | `runKeyed('k', change)` three times within 1000 ms of each other | 1 step |
| Keyed run, slow | two `runKeyed('k', …)` 1001 ms apart | 2 steps |
| Keyed run timing | three keyed changes 800 ms apart (1600 ms from first to last) | 1 step: the window restarts at each change |
| Different keys | `runKeyed('a', …)` then `runKeyed('b', …)` at once | 2 steps |
| Key then plain | keyed change, then a change outside `runKeyed`, then a keyed change with the same key | 3 steps |
| Key inside a group | drag open, `runKeyed('k', change)` twice, close, `runKeyed('k', change)` at once | 2 steps: the group wins, and its step has no key |
| `runKeyed` return and throw | fn returns 7; fn throws | returns 7; the error is rethrown and the previous key is back |
| Undo | 2 steps A then B | `undo()` returns true, the plan is the one before B, `canRedo` true, `lastAnnouncement` `Undone`, `announceCount` +1 |
| Undo empties | undo twice | plan is the one before A; `canUndo` false; a third `undo()` returns false and changes nothing, `announceCount` unchanged |
| Redo | after one undo | `redo()` returns true, plan equals the one after B, `lastAnnouncement` `Redone` |
| Redo with nothing | `redo()` on a fresh history | false |
| New change clears redo | undo, then a change | `canRedo` false; `redo()` false |
| No merge across undo | field open, change, `undo()`, change (field still open), change | after the undo: 1 new step holding both later changes |
| Units kept | change, `setUnits('m')`, `undo()` | plan restored, `units` is still `'m'` |
| References restored | change to `items`, `undo()` | `usePlanStore.getState().items` is the same reference as before the change |
| Undo is not recorded | `undo()` | the store update it makes adds no step |
| Blocked in a drag | drag open, change, `undo()` | returns false, nothing changes; after `closeGroup('drag')` `undo()` works. Same for `redo()` |
| Cap | 101 separate changes | 100 steps; undoing 100 times ends at the plan after the first change |
| Clear | steps exist, `clearHistory()` | `canUndo` and `canRedo` false, `lastAnnouncement` null; an open group is forgotten |
| Stale selection: item | item X selected, undo removes X | `selectedId` null |
| Stale selection: room things | selected corner, wall, opening or obstacle no longer exists after undo or redo (a wall exists when a corner with its id exists) | that selection is null |
| Kept selection | the selected thing still exists after undo | selection unchanged |

**Exact values:** `historyLimit: 100`, `historyMergeMs: 1000` in `CONFIG` (placed after
`saveDebounceMs`). A keyed change joins the latest step when that step has the same key, no
group, and `Date.now() - (time of the step's latest change) <= 1000`.

**Verify:** `npx vitest run room-planner/state/historyStore.test.ts room-planner/domain/catalog.test.ts`
→ all pass; `npx tsc --noEmit` → no errors.
